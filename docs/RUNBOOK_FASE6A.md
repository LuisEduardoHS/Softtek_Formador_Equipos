## Preparación

1. Desde `backend/`, crear el entorno e instalar `requirements.txt`. Configurar `DATABASE_URL` y un `AUTH_SECRET` aleatorio de 32 caracteres o más en `.env` a partir de `.env.example`. No compartir ni registrar ese secreto. El servidor no inicia cambios de esquema automáticamente.
2. En una base **nueva**, crear las tablas con `database/db_actividad.sql`. En una base existente, conservar copia de seguridad, verificar las tablas `usuarios`, `perfiles_usuarios` y `eventos`, y ejecutar `python -m alembic -c alembic.ini upgrade head` desde `backend/`. La revisión `20261022_6a` solo agrega columnas faltantes y no reescribe filas; en una base nueva ya creada con el SQL, igualmente registra la revisión. La reversión automática está deshabilitada porque borraría datos de IA.
3. Arrancar MySQL, Ollama y los modelos `llama3.1:8b` y `nomic-embed-text`; después `uvicorn app.main:app --reload` en `backend/` y `npm run dev` en `frontend/`. React usa `VITE_API_URL`, o `http://127.0.0.1:8000` por defecto. La conexión con MySQL y Ollama debe validarse en el entorno de despliegue; la suite automática usa SQLite y mocks.

## Contratos y estados

- `/auth/registro` y `/auth/login` devuelven `access_token` Bearer con vida de ocho horas. `/auth/me` verifica la sesión. El servidor decide identidad y titularidad; `creador_id` del cliente solo se acepta si coincide con el actor. Un cambio de `AUTH_SECRET` invalida tokens previos. React guarda el token durante la sesión del navegador y valida `/auth/me` antes de las pantallas privadas. Los tokens son independientes del servidor: no hay revocación individual ni refresco en 6A.
- Perfil: `POST /perfil/interpretar` recibe textos y guarda un borrador. Devuelve una sugerencia marcada `ia_sin_confirmar`; no crea habilidades confirmadas. `POST /perfil/confirmar` recibe los campos revisados por la persona y los guarda como `StructuredProfile` confirmado. Genera Nomic desde habilidades, intereses y experiencia confirmados, **sin áreas de mejora**. `GET /perfil/{id}` solo es para el titular. `POST /perfil/embedding/reintentar` reintenta un vector pendiente.
- Evento: `POST /eventos/interpretar` devuelve una sugerencia `ia_sin_confirmar`. React permite revisar roles, obligatorias, deseables y restricciones. `POST /eventos/` crea el evento para el actor; con `requisitos_confirmados` revisados y `confirmado_por_creador=true` lo abre y genera el vector, sin ellos guarda un `Borrador` visible solo al creador. `POST /eventos/{id}/confirmar` permite confirmar un borrador con la misma marca explícita; `/embedding/reintentar` reintenta el vector. El campo anterior `requisitos_ia` está prohibido en el cuerpo de creación. Un requisito declarado explícitamente por el organizador en `requisitos_confirmados` es su declaración, no una extracción verificada automáticamente.
- Los estados de IA incluyen `pendiente_revision`, `interpretacion_pendiente`, `pendiente_embedding`, `sin_contenido`, `listo` y `obsoleto`. `sin_contenido` significa que no hay contenido confirmado suficiente para un vector; no es una caída de Nomic. El fallo de Ollama conserva datos confirmados y deja el vector `NULL`. La UI ofrece reintentar la interpretación o revisar manualmente mientras espera; el borrador de un proyecto aún sin publicar se conserva en `sessionStorage` por usuario y se elimina al publicarlo. Los vectores son JSON `list[float]` de 768 entradas finitas, con modelo, versión de pipeline y revisión SHA-256 de la fuente. No salen en respuestas HTTP.
- El perfil público omite borradores y áreas de mejora salvo consentimiento explícito; un perfil pausado queda fuera del directorio. Los borradores de evento solo son visibles a su autor. Un `PUT /perfil/{id}` legado que cambia datos relevantes invalida el vector hasta nueva confirmación.

La confirmación de un proyecto existente exige `fuente_revision`, la huella vigente devuelta al creador por el detalle, junto con `requirements` y `confirmado_por_creador=true`. Una revisión sin huella se rechaza con 422 y una huella obsoleta con 409. Token e identidad React se guardan en `sessionStorage` de la misma pestaña; `/auth/me` restablece la identidad al recargar. La interpretación comparte solo solicitudes idénticas en vuelo, no resultados guardados; un reintento tras error vuelve a llamar al servicio.

## Verificación y límites

Ejecutar `python -m pytest -q` y `python -m pip check` en `backend/`, y `npm run build` en `frontend/`. Las pruebas de 6A usan DB temporal y mocks de parser/vector para cubrir 401/403, persistencia, errores recuperables y migración aditiva. No ejecutan MySQL ni Ollama reales. Revisar la estructura real de MySQL antes de migrar producción; `create_all` fue retirado del arranque. La UI de Fase 6A no muestra recomendaciones del motor de Fase 5. Las notificaciones simples existentes de Isaac siguen siendo un flujo separado y su sustitución corresponde a 6B.
