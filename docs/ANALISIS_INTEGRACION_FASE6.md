## 3. Arquitectura observada y contratos que aún no conectan

### Identidad, acceso y perfiles

- `backend/app/api/routes/auth.py` registra usuarios y verifica contraseña, pero `/auth/login` devuelve datos de usuario sin token ni sesión de servidor. `frontend/src/services/api.js` guarda/lee el usuario de `localStorage`; incluso en Isaac, `session.js` es ayuda de UI, no credencial verificable. `GET/PUT /perfil/{usuario_id}`, `POST /eventos/` con `creador_id`, `POST /invitaciones/?de_id=`, `PATCH /invitaciones/{id_solicitud}`, `GET /equipos/{id_usuario}` y `GET /notificaciones/{id_usuario}` carecen de una dependencia de identidad/autorización de servidor. Un ID suministrado por el cliente no demuestra titularidad. **Bloqueante para exponer Fase 6.**
- `perfiles.py` crea/actualiza `datos_crudos` y `atributos_dinamicos`; `PerfilUpdate.datos_crudos` admite JSON genérico. La proyección pública oculta algunos campos por `visibilidad` y `pausado`, pero el GET privado por ID entrega correo y JSON completo sin comprobar actor. El directorio `/perfil/estudiantes/` filtra `estado_cuenta="Activa"` y perfiles pausados, mientras la política de descubrimiento de Fase 5 necesita consentimiento/visibilidad global confirmados y hechos con procedencia. La API todavía está nombrada para estudiantes y `Usuario.carrera` es obligatoria aunque el producto abarca deportes, emprendimientos y otros.
- Los campos UI `fortalezas`, `reforzar`, `intereses`, `disponibilidad`, `visibilidad` y `pausado` viven en `datos_crudos`. `StructuredProfile` usa `habilidades`, `intereses`, `areas_mejora`, `experiencia`, `resumen_publico`; `CandidateInput` exige evidencias tipadas y separa `None` de `[]`. No existe adaptador que convierta declaraciones en `Evidence(source="user_declared", kind, polarity, confirmed)` ni revisión explícita de extracción IA. El mapeador del frontend asigna por defecto nivel `intermedio` a habilidades de texto: **no debe elevarse a nivel de competencia confirmado**.

### Eventos, equipos y solicitudes

- `eventos.py` guarda `descripcion_libre`, `detalles_especificos`, `requisitos_ia` recibido del cliente y `embedding_requisitos={}`; no llama `EventParser` ni `generate_event_embedding`. El frontend envía `requisitos_ia: {roles}` y también roles dentro de `detalles_especificos`; `StructuredEventRequirements` espera listas separadas de obligatorias, deseables, roles, intereses y restricciones. Ningún campo actual marca qué requisitos revisó el organizador. Las categorías del mapper de `api.js` colapsan cualquier evento no `Personal` a `academico`, perdiendo la distinción deportiva/videojuegos/general que requiere matching.
- El SQL y el ORM incluyen `participantes_evento` y `solicitudes_equipo`. `origin/isaac` mejora la respuesta de invitaciones, equipos y transiciones aceptada/rechazada; al aceptar agrega `ParticipanteEvento` en el mismo `commit` de sesión. Aun así, `SolicitudUpdate.estado` es un `str` libre (la ruta valida), el rol propuesto viaja incrustado en `mensaje_explicacion`, y la aceptación no comprueba que quien responde sea el destinatario, que el evento siga abierto o que la persona sea elegible. La consulta previa para evitar invitación pendiente no tiene garantía transaccional ni índice único de solicitudes; existen carreras y posibles acciones inversas duplicadas. El SQL declara `UNIQUE(id_evento,id_usuario)` para participantes, pero el ORM no refleja esa restricción; verificar la tabla real antes de depender de ella.
- La nueva `GET /notificaciones/{id_usuario}` de Isaac calcula en cada lectura sugerencias por intersección textual de habilidades y roles, devuelve nombre del candidato y marca `grupo="ia"`. No usa `recommend_candidates`, elegibilidad, evidencia confirmada, política/versiones, restricciones ni freshness. El `id_usuario` de ruta carece de autenticación; sus resultados no deben confundirse con recomendaciones Fase 5. Además consulta todos los perfiles activos para cada organizador y compone resultados por rol, con riesgo de costo, duplicados y exposición si cambian permisos. El payload de `/equipos/{id_usuario}` incluye `embedding_requisitos` del evento, aunque la UI no necesita el vector.

### IA, matching y recomendaciones

- `ProfileParser` y `EventParser` generan estructuras Pydantic desde Ollama; `generate_profile_embedding` y `generate_event_embedding` producen listas finitas, y con `nomic-embed-text` validan **768 dimensiones**. El parser recibe texto libre; el JSON estructuralmente válido no garantiza que el hecho sea cierto. Los casos de regresión IA-01 a IA-05 y las pruebas puras reducen riesgos conocidos, pero no equivalen a evaluación semántica en producción. `embeddings.py` omite `areas_mejora` del texto de perfil.
- `OllamaClient` usa timeout de 120 s y errores controlados, pero las rutas actuales no invocan IA, no hay estado de procesamiento, reintentos ni cola. Integrarlo directamente en POST/PUT podría bloquear peticiones; definir flujo desacoplado e idempotente. No enviar PII innecesaria a Llama para explicaciones; `personalize_recommendation` solo permite seleccionar variantes de hechos ya aprobados y conserva fallback determinista.
- `matching/` implementa `Evidence`, `CandidateInput`, `EventInput`, `RequirementAssessment`, `MatchResult`, normalización/equivalencias versionadas, elegibilidad, complementariedad, coseno y ranking. Política inicial: 0.40 obligatorias, 0.25 complementariedad, 0.15 deseables, 0.10 coseno, 0.10 intereses. Datos desconocidos no se convierten en incumplimiento; solo una contradicción confirmada puede activar filtros estrictos configurados. Vectores ausentes/incompatibles dan `None`, no cero.
- `recommendations/` local (aún sin seguimiento) implementa resultados públicos para organizadores y usuarios, explicaciones deterministas con reformulación opcional controlada, duplicados y huellas de vigencia `current/stale/unknown`. Es un motor **puro**: los contextos `OrganizerRecommendationContext` y `UserRecommendationContext` suponen que un adaptador ya verificó permisos, visibilidad, membresía y acciones. No hay todavía fuente confiable de `SourceVersions`; no publicar `current` por defecto. Los DTO públicos no contienen scores ni embeddings. Una huella `current` tampoco autoriza una invitación posterior.

## 4. Flujo integrado propuesto y fronteras

1. **Identidad y autorización.** El servidor autentica al actor, identifica su usuario sin aceptar un ID sustituto del navegador y decide si puede leer/editar perfil, evento, equipo o recomendaciones. El frontend usa la sesión para experiencia de usuario; el backend decide el acceso.
2. **Escritura de fuentes.** Perfil y evento guardan texto original y cambios declarados por el autor. La extracción IA se procesa aparte, con estado, revisión de fuente, modelo/pipeline y error recuperable. Un resultado del parser no se convierte en hecho confirmado por defecto. El organizador revisa requisitos y vacantes; el usuario confirma sus declaraciones.
3. **Embeddings.** Generar Nomic para una revisión concreta de perfil/evento, almacenar vector finito de 768 dimensiones más modelo/pipeline, revisión fuente y fecha/estado. Si cambia la fuente, marcar el vector obsoleto y regenerar. Coseno solo con vectores compatibles y vigentes; sin vector continuar con señales explícitas.
4. **Lectura de instantánea para recomendaciones.** En consultas por lotes y dentro de permisos, obtener evento, perfiles visibles, participantes, solicitudes/invitaciones y revisiones. Un adaptador transforma SQL/ORM a `EventInput`, `CandidateInput`, `Evidence`, contextos y `SourceVersions`. `None` representa consulta/dato desconocido; `[]` significa comprobado vacío. Los requisitos extraídos sin revisión son `ai_unreviewed`.
5. **Motor puro.** Ejecutar `recommend_candidates` o `recommend_projects` con política y catálogo versionados. Aplicar elegibilidad antes de ranking, omitir perfiles ocultos, creadores, miembros y pares con acciones pendientes. Proyectar solo DTO público y explicación sustentada; Llama es opcional para una petición expresa y nunca decide el orden.
6. **Presentación y vigencia.** El endpoint resuelve únicamente datos públicos permitidos para su audiencia, junto con un indicador de cobertura y vigencia calculada a partir de metadatos reales. `unknown` no se presenta como `current`. La UI separa elegibles de casos `needs_review` y no trata el score interno como porcentaje.
7. **Acción posterior.** Antes de invitar o solicitar ingreso, una **operación de escritura transaccional** vuelve a comprobar actor, propiedad/consentimiento, visibilidad, evento abierto, requisitos estrictos, vacante/cupo, membresía, pendientes y estado de la recomendación. Aplicar unicidad/idempotencia en BD y manejar conflicto concurrente. La recomendación mostrada es orientación, no permiso para actuar.

### Primer encargo sugerido

**6.1, solo identidad y permisos de servidor.** Es el bloqueo más fuerte: hoy una persona puede indicar IDs ajenos en rutas de perfil, equipo, invitaciones o notificaciones, y ningún contexto de Fase 5 puede considerarse autorizado si se construye sobre esos IDs. Entregar primero una matriz de permisos acordada y pruebas de acceso cruzado con la interfaz de actor autenticado; después conectar adaptadores de lectura. Este encargo debe coordinarse con el responsable de autenticación, sin mezclar en la misma entrega cambios de IA, migraciones o UI.

## 6. Riesgos y preguntas pendientes

1. **Seguridad alta:** rutas actuales y nuevas carecen de identidad de servidor; notificaciones pueden revelar nombres, proyecto y coincidencias por ID manipulable. La ruta de equipos entrega vectores. No publicar recomendaciones reales antes de resolverlo.
2. **Fuentes de verdad:** `requisitos_ia` es escribible desde frontend y no distingue extracción de confirmación; `fortalezas` en JSON tampoco conserva procedencia/negación. Definir quién confirma cada hecho y cuándo se revoca.
3. **Paridad de datos:** SQL, ORM, `EventoOut` y frontend divergen en perfil IA, vector, rol y categoría. El esquema real puede diferir; `create_all` no sirve como plan de migración.
4. **Concurrencia:** una recomendación puede pasar de válida a obsoleta antes de la acción; los checks de pendiente en consultas separadas no evitan doble envío. La operación final necesita control transaccional y restricciones comprobadas.
5. **Rendimiento y operación:** el cálculo por lectura de notificaciones de Isaac recorre perfiles por evento; el procesamiento Ollama puede durar hasta 120 s. Definir límites, lotes, caché/invalidación y estado de procesamiento antes de producción.
6. **Evaluación:** 168 pruebas locales y build verde prueban reglas y compilación, no precisión semántica real, calidad del ranking ni seguridad HTTP. Las novedades remotas no traen pruebas y no se ejecutaron en esta rama.

**Siguiente decisión de Git:** conservar y registrar conscientemente el trabajo local de Fase 5, revisar con Isaac la coexistencia de notificaciones y recomendaciones, y repetir preflight con árbol limpio. Solo entonces considerar un merge normal de `origin/isaac`, seguido de pytest, `pip check`, build frontend y pruebas de integración de contratos. Este documento no efectúa esa decisión.
